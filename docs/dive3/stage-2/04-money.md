## 2.4 Money

This section covers every place money is recorded, priced, moved and reported. Read it in four passes. Start with the ledger and the wallet lock, then charges and pricing. Then read cash-in, cash-out and payouts, with the payment webhook and a payout taken back after payment. End with accounting and reconciliation. For each method that moves money, the entry names its locks in order, the `ledger_record` rows it writes and what makes a retry harmless. A retry is the same request arriving twice, from a double click or a resend. Read `wallet-request.service.ts` slowly. The worker section covers the jobs that bill storage, recompute usage tiers and accrue interest. The section takes about 40 minutes.

#### `apps/api/src/modules/pay/ledger.service.ts`

About 2 minutes. It builds on T8.1, T8.2 and T8.3.

This file writes the wallet ledger and owns the wallet lock. A wallet's balance is the sum of its `ledger_record` rows. `PayModule`, the money module `pay`, is global, so any module that moves money can inject `LedgerService`. `record` appends one row inside the caller's transaction `tx`. The `amount` is always a positive number of cents, and `direction` says whether the row is a credit or a debit. The database refuses UPDATE and DELETE on these rows, so a mistake is undone only by a second row that reverses it. `WalletRequestService` writes its `withdrawal` and cash-in `credit_topup` rows without `record`, to get the new row's id. The worker jobs write rows in raw SQL.

`lockWallet` takes the wallet lock, a Postgres advisory lock on the key `wallet:` plus the user id. It lasts until the transaction commits or rolls back, and taking it twice is harmless. It needs a transaction, because outside one Postgres releases it at once. `balanceOf` adds up the credits and subtracts the debits. Given a `tx`, it takes the wallet lock first, so no other spend can read the balance until the caller's debit is saved. Without a `tx` it is a plain read, fine for showing a balance but not for deciding to spend it. `list` returns one user's rows, newest first, with `id` breaking a tie, so the withdrawal and fee debits of one cash-out keep their order and the running balance on the wallet screen does not change between loads. A row that pays a `charge` also carries `chargeAction`, the charge's action type, and `chargeItemClass`, read from the `itemClass` of the rule snapshot recorded with the charge, so the statement can say what the charge was for. The join matches the charge on its id and on the same user, and every other row carries null in both.

Every money path locks the business rows first, such as the listing, the request or the shipment, then the wallet, then the user's honoured membership period. With one order, two transactions wait for each other but never deadlock, as T8.3 explains. The worker job `interest-accrual.ts` builds the same lock key in raw SQL. If you rename the key here, they stop waiting for the API and can charge a wallet the API is spending from. `EscrowService.settle` locks the deal, then the wallet of the raiser, who pays the escrow fee, then the raiser's period. Since migration `0046` a settled charge, a fee or a refund also runs `recompute_usage_tier` through a trigger in the same transaction. Since migration `0047` that function first takes the account's `user_account` row `FOR NO KEY UPDATE` and holds it to the commit, so the account row is the last lock a money path takes. `FOR NO KEY UPDATE` and not `FOR UPDATE`, because the charge's own foreign key already holds a key-share lock on that row, and two charges for one account that both asked for `FOR UPDATE` deadlocked on the upgrade. A path that charges two accounts, such as a swap, takes their account rows in the order it charges them, but `TradeService.approve` first locks both wallets in user-id order, so two swaps between the same two collectors in opposite directions queue on the first wallet instead of deadlocking on the account rows.

#### `apps/api/src/modules/pay/pay.schema.ts`

About 2 minutes. It builds on T5.3, T8.1, T8.2 and T8.4.

This file defines the tables of `pay`, and none of them stores a balance. This section writes six of the fourteen `ledgerRecord` types. `credit_topup` is a credit from `CheckoutService.checkout`, from `PayPalCheckoutService.settle`, from `CryptoCheckoutService.settle` and from `settleInOneStep` for a cash-in. `withdrawal` is the net debit in `debitCashOut`. `fee` is a debit for the cash-out fee, the chargeback fee and `BillingService.charge` on `marketplace_fee`. `service_charge` is a debit from `BillingService.charge` for other actions. `chargeback` is a debit from `ChargebackService.record` and `recordCashInRecall`. `payout_reversal` is a credit from `recordPayoutOutcome` and `reversePaidPayout`. The other eight types come from other sections. `ledger_record_interest_daily_unique` allows one `interest` row per user per UTC day, so a rerun of the accrual job adds nothing. The check `ledger_record_amount_positive` refuses an amount of zero or less. It is `NOT VALID`, so Postgres applies it only to rows written after migration `0036`.

`externalPayment` is money at a provider. Its `purpose` is `topup` or `payout`, and its `status` is free text, one of `pending`, `succeeded`, `failed`, `refused`, `reversed` or `cancelled`. A PayPal or crypto checkout the collector left is `cancelled`. For a PayPal checkout, `externalRef` is the order id, `captureRef` the capture id and `providerFeeMinor` the fee PayPal kept. `charge` is the priced reason behind a fee. Its `pricingRuleSnapshot` freezes the rule, and accounting reads the keys `cashOutFee`, `chargebackFee`, `escrowFeeBps` and `carrierCost` from it. The cash-out fee is stored under the action type `cash_out_fee` and the chargeback fee under `chargeback_fee`, so the statement names each from its own price-list rule. Migration `0048` moved the rows written before that off `service`, and they keep their snapshot key, which is what accounting reads. `walletRequest` holds a request, and `walletRequestEvent` is its append-only history. `settledLedgerId` and `payoutPaymentId` link a request to the ledger row and the payment it created. Only the seed writes the `withdrawal` table, which is not the ledger type, and the API never uses it.

The other retry guards are unique indexes in the migrations. `wallet_request_settled_ledger_unique` from `0004` lets one ledger row settle only one request. `external_payment_provider_ref_unique` from `0017` allows one payment per provider reference. Migration `0031` adds three more. `wallet_request_payout_payment_unique` lets one payment pay only one request. `external_payment_external_ref_unique` allows each external reference once per provider, and `external_payment_webhook_event_unique` allows each webhook event id once. Migration `0040` adds two. `external_payment_capture_ref_unique` lets one PayPal capture settle one payment only. `ledger_record_one_credit_per_payment` allows at most one `credit_topup` citing an `external_payment`, so a second credit for a payment fails its transaction even if the code tried to write it.

#### `apps/api/src/modules/pay/wallet.service.ts`

About 1 minute. It builds on T8.1, T8.7 and T8.9.

`WalletService` shows a wallet and blocks new work while it is in debt. `balance` and `ledgerList` back `GET /finance/wallet` and `GET /finance/ledger`. `cashOutQuote` returns `cashOutSettlement` plus the fee bands, `limits` and `withinLimits`, which says whether the amount could be cashed out at all, and completion debits from the same function. `CashOutQuoteQuery` takes `amountMinor` as a whole number of cents from 1 to `CASH_OUT_QUOTE_MAX_MINOR`, so anything else is a 400. The quote applies no membership waiver, so a member may pay less than quoted. `assertNotBlocked` answers 409 `NEGATIVE_BALANCE_BLOCKED` when the balance is below zero. `ServiceRequestService`, `ShipmentService.create`, `DirectShipService` and `HumanFulfilmentService` call it without `tx`, so it takes no lock. For them it is only a check at the door, because a debit can land just after it. `CustomRequestService` is the exception: it passes its `tx`, so the check takes the wallet lock and holds it to the end of that transaction.

#### `apps/api/src/modules/pay/billing.service.ts`

About 2 minutes. It builds on T8.4, T8.5, T12.3 and T15.2.

`BillingService` charges a fixed price for an action that another module performs. It implements `BILLING_PORT`, which the inbound module `inv`, the services module `dis` and the marketplace module `mkt` call inside their own transaction. `charge` first calls `MembershipService.consume` on `allowanceFor(feeActionType ?? actionType)`. If an allowance covers the action, `charge` writes nothing and returns `covered` with the period and the allowance. Otherwise it prices the action with `tryPrice(feeActionType)`, or else with `price(actionType)`, and passes `itemClass` and the account, so the price is the account's tier price. A zero price writes nothing and returns `free`. Any other price inserts a settled `charge` and one debit, and returns `charged` with the charge's id and amount. The debit is `fee` for `marketplace_fee` and `service_charge` for the rest. No caller sends `marketplace_fee` through the port, so in practice every debit here is a `service_charge`.

`charge` takes no lock of its own, but `consume` locks the period row with a conditional UPDATE. So a caller that needs the wallet lock must take it before `charge`, to keep the wallet ahead of the period. A retry is safe because the charge commits or rolls back with the caller's work.

`charge` checks no balance and may take the wallet into debt, so callers refuse new work with `assertNotBlocked`. It passes no `base`, so an action priced here must have a `fixed` rule, and `PricingService` refuses a percentage with nothing to take it of. `PayModule` is the only provider of the port; the old `BillingModule` and its `NoopBillingAdapter`, which only logged and charged nothing, were removed.

#### `apps/api/src/modules/prc/pricing.service.ts`

About 2 minutes. It builds on T8.4, T8.5 and T5.5.

`PricingService` finds the rule in force and computes the amount, for `BillingService` and the services that price their own fees. `ruleInForce` reads the action's rules whose `item_class` is null or the given class. A rule is in force when `effective_from` is not after now and `effective_to` is null or later. A rule for the class beats the catch-all through `nulls last`, and then the newest rule wins. When no rule is in force, `ruleInForce` and `tryPrice` return null. Otherwise a `fixed` rule gives `value` in cents, and a `percentage` rule gives `applyBasisPoints` of `base`. A percentage with no `base` is a 400. When the caller passes `userId`, `tryPrice` reads the account's `usage_tier` and takes the tier's `discountBps` off through `discountedMinor`, so a Silver account pays 10 percent and a Gold account 20 percent under the list price, and the `snapshot` adds `tier`, `discountBps`, `listMinor` and `chargedMinor`. The snapshot is stored on the `charge`, or on the transaction for a sale's fee, so a later tier change never changes a past charge. `quoteFor` gives the same four fields for a price that is not a rule, such as a house-store card or a show's own pickup fee. Every caller that charges an account passes it: billing, marketplace and consignment fees, shipment handling, rush and add-ons, show pickups, the house store and the admin storage run. The fees charged from code constants, such as the escrow, cash-out and chargeback fees and the insurance premium, and an operator's white-glove quote, are not priced here and are the same for every tier. Any other error, a database failure included, reaches the caller. `price` is `tryPrice` with a 400 when no rule is in force. `createRule` inserts a rule effective now and never edits one. It needs a description, and it allows a percentage only for an action whose `percentOf` names its base, at most 10,000 basis points.

Only migration `0046` writes `effective_to`, to end the `membership:` rules. Otherwise a rule ends only when a newer rule for the same scope replaces it. A class rule keeps beating a newer catch-all, so a new catch-all price never reaches that class. The in-force test is repeated in `PriceListService`, `PricingCoverageController`, `VaultService` and the worker job `storage-fee.ts`. Change them together, or they will disagree with the API.

#### `apps/api/src/modules/prc/price-list.service.ts`

About 1.5 minutes. It builds on T8.5.

`PriceListService` builds the public price list, and `publicList` backs `GET /pricing/list`. It takes the rules in force and keeps the newest for each `actionType` and `itemClass`. `groupFor` sorts them into `PRICE_GROUPS`. It checks prefixes first, and an unknown action lands in `services`. The list shows rules, not charges. So a `code_constant` action, such as the cash-out, chargeback or escrow fee, shows its rule while the code charges a constant, and the two can differ. Each entry carries `tierDiscounted`, false for those and for the white-glove bases, so the page shows them at list price to every tier.

#### `apps/api/src/modules/prc/billable-actions.ts`, `apps/api/src/modules/prc/pricing-coverage.controller.ts`

About 2 minutes. It builds on T8.5.

These files tell an admin before launch whether every price the code charges has a rule. Only the seed inserts a `pricing_rule`, never a migration, so an unseeded database has no prices. `billableActions` lists every price the code charges, each with a `PriceResolution` that says what a missing rule does. `required` means the action fails. `fallback_rule` uses a broader rule, and `code_default` uses a figure in the code. `free_if_unpriced` charges nothing, and `code_constant` never reads a rule. The families come from `GRADING_TIERS`, `CONSIGNMENT_CHANNELS` and `SHIPMENT_ADD_ONS`. `percentOf` names the amount a percentage is taken of, such as the sale price, the agreed value or the amount cashed out. A null `percentOf` means fixed prices only.

`coverage` is `ready` only when every action is `priced` or `code_constant`, and only a catch-all rule makes an action `priced`. Its `unknownRules` lists rules that no code reads, usually a typo. `PricingCoverageController.coverage` serves `GET /admin/pricing/coverage` to admins. `tests3/contract/pricing-coverage.test.ts` scans the source for literal action types, so a new literal passed to `price` or `tryPrice` must be listed here or the test fails.

#### `apps/api/src/modules/prc/prc.schema.ts`, `apps/api/src/modules/prc/prc.controller.ts`, `apps/api/src/modules/prc/prc.module.ts`

About 1.5 minutes. It builds on T5.5, T6.2 and T8.5.

These files hold the table and routes of the pricing module, `prc`. `pricingRule` holds effective-dated rows. Each has an `actionType`, an `itemClass` where null is the catch-all, a `model` of `fixed` or `percentage`, and a `value` in cents or basis points. It also has `billingTrigger`, `parameters` for terms such as storage, `effectiveFrom`, `effectiveTo` and `updatedBy`. `actionType` is free text, so a typo makes a rule that nothing charges, and only `unknownRules` shows it. `PrcController` serves the public `GET /pricing/list`. `GET /pricing/rules` returns every rule ever made, so it carries `@Roles('admin')`, and the admin console is its only reader. `POST /pricing/rules` is for admins and takes `CreateRuleDto` with a `value` of zero or more, an `actionType` and `itemClass` of at most 80 characters and a `description` of at most 300. `createRule` also refuses a fixed price above `MAX_FIXED_PRICE_MINOR`, $10,000, so a typed extra zero is a 400 and not a live price. `PrcModule` is global and exports only `PricingService`.

#### `apps/api/src/modules/pay/money-terms.ts`

About 1.5 minutes. It builds on T8.6, T8.7 and T8.8.

This file holds the fixed figures for the cost of moving money. Up to `CASHOUT_BAND_MINOR`, which is $100, `cashOutFeeMinor` charges 6 percent with a $0.99 floor. Above the band it charges $5 plus 1 percent. It always rounds up. `cashOutSettlement` returns `grossMinor`, `feeMinor` and `netMinor`. The gross leaves the wallet, the customer receives the net, and a membership waiver lowers only the fee. The quote, the payout and the ledger all call `cashOutSettlement`, so their figures agree. `CHARGEBACK_FEE_MINOR` is $25. `CASHOUT_FEE_ACTION` and `CHARGEBACK_FEE_ACTION` are the action types the two fees are stored under, and they name the price-list rules the statement reads its words from, but the amounts come from the constants here, never from those rules. `FUNDING_ROUTES` and `isInstantRoute` say which routes settle on their own. A provider confirms `card` and `paypal_gs`, through PayPal checkout once it is switched on, and a person must see `paypal_ff` and `bank_transfer` arrive.

#### `apps/api/src/modules/pay/wallet-request.rules.ts`

About 1.5 minutes. It builds on T8.6 and T8.7.

This file holds the request lifecycle and limits, with no database. The SPA repeats the statuses, limits and draft checks in `apps/web/src/shared/walletRequests.ts`, so change both together. `WALLET_REQUEST_TRANSITIONS` lists the allowed moves between nine statuses. The main path runs from `submitted` through `pending_review`, `approved` and `processing` to `completed`. A reviewer may skip `pending_review` and `processing`. The requester may cancel while a request is `submitted` or `pending_review`, and a reviewer may reject any open request. A provider payout adds `paying`, which leads to `completed` or `payout_failed`. Only `reversePaidPayout` takes `completed` to `payout_failed`, and nothing leads from `paying` to `rejected`. The service checks a move against this table only through `canTransition`.

`OPEN_WALLET_REQUEST_STATUSES` lists the four undecided statuses. `paying` is not one, because its money has already left the wallet. `WALLET_REQUEST_LIMITS` allows a cash-in of $10 to $20,000 and a cash-out of $20 to $20,000. `validateWalletRequestDraft` checks every rule that needs no database, including a destination of at most `MAX_DESTINATION_LENGTH`, 140 characters, which every route shares, and its messages are written for a person, with limits in dollars through `formatMinor` and the funding sources in words. The balance check needs the database, so it is in the service, and the duplicate rule lives only in the SQL of `submit`.

#### `apps/api/src/modules/pay/wallet-request.service.ts`

About 3 minutes. It builds on T8.6, T8.7 and T15.2.

This service runs every reviewed cash-in and cash-out, from submission to payout and reversal. Submitting never moves money. Only a completion, a refused payout or a payout taken back after payment writes ledger rows. Reviewers are admins, and `assertSeparationOfDuties` bars the requester from deciding their own request. One admin can still approve and complete the same request, and Stage 3 decided to keep it that way while the beta runs with one administrator.

`submit` refuses a request identical to an open one, and a cash-out above `balanceOf`. Both checks read without a lock, so two submits at once can both pass, and completion checks the balance again under the wallet lock. `submit` writes the request, a `submitted` event, an outbox row and an audit row. `cancel`, `markUnderReview`, `approve`, `reject` and `markProcessing` go through `applyTransition`. In one transaction it locks the request `FOR UPDATE` and checks `canTransition`. It then writes the update, the event, the outbox row `wallet_request_<status>` and the audit row. `listForReview` reads a date-only `to` such as `2026-10-15` as the end of that UTC day, so that day's requests are in, and a full time as that instant. It returns everything newest first unless the caller passes `limit`, at most `REVIEW_QUEUE_MAX_LIMIT`, and then `before`, the id of the last request of the previous page, continues from there in `(created_at, id)` order. The console does not page yet, so it still loads the whole queue.

`complete` sends a cash-in to `settleInOneStep`. A cash-out goes there too when `PAYOUT_MODE` is `manual`, and then it needs the `payoutReference` of the admin's manual payment. In `provider` mode a cash-out goes to `payOut`, and a reference is refused. Both paths start with `lockForCompletion`, which locks the request `FOR UPDATE` and checks separation of duties. It refuses a request that is `completed` or `paying`, a move that `canTransition` forbids, and a request whose `settledLedgerId` is set. A `rejected`, `cancelled` or `payout_failed` request is refused in words from `CLOSED_FOR_COMPLETION`, and only an undecided one is told to be approved first. Separation of duties compares the owner of the row it locked with the session's own id, never the id written in the path, so an id in upper case is refused the same way. For a cash-out, `debitCashOut` then computes the fee from the current schedule. It takes `lockWallet`, calls `memberships.waive` on `cash_out_fee`, which locks the period, and checks `balanceOf` against the gross. A shortfall is a 409, and the whole transaction rolls back, waiver included.

For a cash-in, `settleInOneStep` locks the request, then the wallet, and writes one `credit_topup`, so the interest job never reads the balance between that credit and its own insert. If Complete is clicked twice, the second call waits on the request lock. Then `lockForCompletion` refuses it as `completed`, so the money is credited once. For a manual cash-out it locks the request, then the wallet, then the period. It writes a `withdrawal` debit for the net and a `succeeded` `external_payment`. When a fee remains after any waiver, it also writes a `fee` debit with its `charge`. The same check makes a retry safe. An external reference is unique per provider, so one transfer cannot pay two requests.

`payOut` takes three steps, because a PayPal payout cannot share a database transaction. Step 1 locks the request, then the wallet, then the period. It commits the `withdrawal` and `fee` debits, a `pending` payment and the `paying` status before PayPal is asked. Step 2 calls `createPayout` outside any transaction, under the 20-second `PAYOUT_PROVIDER_TIMEOUT_MS`, and holds no lock. Step 3 is `recordPayoutOutcome`. If the provider is silent, or fails with any error but a `PaymentProviderError` marked `refused`, the admin gets a 502 and the request stays `paying`. The provider may have paid, so the debit stands until the outcome is known. A refusal commits `payout_failed`, then answers 409. A second Complete is safe, because `lockForCompletion` refuses `paying`. The payment's unique `provider_ref` is `payoutKey(id)`, and the provider uses it as an idempotency key, so a resend never pays twice.

`recordPayoutOutcome` locks the request, then the payment, both `FOR UPDATE`. Apart from a reversal after payment, it acts only on a `pending` payment of a `paying` request. It logs and ignores a later answer, so a repeat changes nothing. Success writes no ledger row, since step 1 wrote the debits. A refusal also locks the wallet, then the period, writes a `payout_reversal` credit for the gross, and through `refundCashOutFee` marks the cash-out fee's `charge` `refunded` in the same transaction. `reversePaidPayout` handles a payout taken back after payment. It runs under the caller's two row locks, then takes the wallet and the period. It writes a `payout_reversal` credit for the gross, marks the fee's `charge` `refunded` the same way, and marks the payment `reversed`, so a repeated event finds nothing `succeeded`. Its `payout_failed` event carries `afterPaid: true`, and so does the `wallet_request_payout_failed` outbox row, so the collector reads that the payout came back after it was sent, not that it could not be sent. Both paths give a used waiver back through `restoreCounted`, and both credit the gross, fee included. Stage 3 decided to keep this, and the cash-out terms say so.

`payingMetadata` reads the fee, the net and the waiver from the `paying` event, and `restoreCounted` needs the waiver. Keep those fields in that event, or a refused payout keeps the member's waiver spent. `applyPayoutEvent` matches a webhook event by `payoutKey`, through `sender_item_id` or `sender_batch_id`, or by the batch id. `reconcilePayouts` asks again about `pending` payouts, by a lookup on `externalRef` or a resend under the same key. It asks about nothing else, so a reversal after payment arrives only by webhook. No worker job runs it, so an admin must.

#### `apps/api/src/modules/pay/wallet-request.controller.ts`

About 1.5 minutes. It builds on T6.2, T8.6 and T8.7.

`WalletRequestController` serves the wallet request routes, with the customer's under `/finance/wallet-requests`. Review routes sit under `/admin/wallet-requests` with `@Roles('admin')`, and `POST /admin/payouts/reconcile` calls `reconcilePayouts`. `SubmitWalletRequestDto` is one shape for both types, and `validateWalletRequestDraft` decides which fields each type needs. `documentKey` must pass `IsObjectKey`. `GET /admin/wallet-requests` answers newest first, at most `limit` rows, 100 when no `limit` is asked for and never more than `REVIEW_QUEUE_MAX_LIMIT`, 500, and `before` takes the id of the last row of the page before; the admin desk asks for 100 at a time and offers "Show older requests" while a page comes back full (`tests/integration/pay-review-fixes.test.ts`, `tests/ux/wallet-desk.test.tsx`). `ReviewQueueQuery` checks dates with `QUEUE_DATE` and strict ISO 8601, so a bad date is a 400 and not a 500. `ReconcileDto` takes `olderThanMinutes` from 0 to 10,080 and `limit` from 1 to 200. No route takes an idempotency key. A double-clicked Complete is safe because of the row lock and the status checks. A collector receives a reduced view through `collectorWalletRequestView` and `collectorDetail`, without the user id, document key, payout ids and reference, reviewer, settled ledger id, payout row, or their own name and email, and each history entry carries `byStaff` in place of the actor, with a reason only when it is the rejection, the collector's own cancel, or a fixed sentence for a failed payout, one for a payout that could not be sent and another, keyed on `afterPaid`, for one that came back after it was sent.

#### `apps/api/src/modules/pay/checkout.service.ts`

About 2 minutes. It builds on T8.6, T6.5 and T4.3.

`CheckoutService` lists the funding routes and runs the sandbox's direct top-up on an instant route. `instantAvailable` is true only with `PAYMENT_PROVIDER=sandbox`, which production refuses at boot. It must stay so, because `checkout` with PayPal would capture whatever order id it was handed, another collector's included. `routes` takes the environment and returns `FUNDING_ROUTES` with the bank and PayPal Friends and Family details, and a route without details is `available: false`. Each route has a `checkout` field. With `PAYPAL_CHECKOUT_ENABLED` on, `card` and `paypal_gs` are available with `checkout: 'paypal'`, and the SPA pays them through `PayPalCheckoutService`. With it off they are `checkout: 'direct'` and available only in the sandbox, so the live site keeps every cash-in a reviewed request, as T1.4 explains, until the owner turns the switch on. Bank transfer stays beside them either way. With `CRYPTO_CHECKOUT_ENABLED` on, a `crypto` route with `checkout: 'crypto'` follows PayPal Goods and Services, paid through `CryptoCheckoutService`. `listMine` backs `GET /finance/payments`, and `collectorPaymentView` gives each cash-in only its id, the route in words from `cashInRouteLabel`, its status, amount, currency and time. It sends no user id, no provider reference, which embeds the user id and the key, no order, capture or webhook id, and not the fee PayPal kept, which is Bault's business. No screen reads the route yet, and it stays for an API client and a later history list.

`checkout` checks the route and the limits. It inserts a `pending` `external_payment` with the `provider_ref` `<route>:<idempotencyKey>` through `onConflictDoNothing`. Only then does it call `createTopup`, outside any transaction. A `failed` answer marks the row `failed`. A settled amount or currency other than the one asked marks it `refused` and credits nothing. Otherwise one transaction records the answer with a conditional UPDATE that needs the row still `pending`. On `succeeded` it takes the wallet lock, then writes one `credit_topup` and a `topup_settled` outbox row. A credit needs no balance check, but the interest job reads the balance under the same lock, so a credit that skipped it could land between that read and the interest insert.

If the same top-up arrives twice, `external_payment_provider_ref_unique` admits one row for the reference. The second call gets the first row back with `replayed: true`, and the provider is not asked again. The same key with another amount or route, or from another user, gets `IDEMPOTENCY_KEY_REUSED`, as PayPal and crypto checkout answer. A provider error is a 502 `PROVIDER_UNAVAILABLE` that leaves the row `pending` for good. Nothing asks the provider again, so the customer may have paid with nothing credited. Reconciliation lists the row under `pending`.

#### `apps/api/src/modules/pay/topup.service.ts`

About 2 minutes. It builds on T8.7 and T15.3.

`TopupService` receives the payment webhook. `handleWebhook` runs `verifyWebhook` on the whole delivery. A `WebhookVerificationError` becomes a 400 `WEBHOOK_UNVERIFIED`. A `refused` verification is logged as an error and reported, and a `malformed` one as a warning. Any other error stays a 5xx, so PayPal sends the event again. An event with no id is `ignored`, and an id already on a payment's `webhook_event_id` is a `duplicate`. A checkout event, `CHECKOUT.ORDER.APPROVED` or a `PAYMENT.CAPTURE` one, goes to `PayPalCheckoutService.applyEvent`, and any other to `applyPayoutEvent`. `handleWebhook` takes no lock, and the service it calls takes the locks.

The duplicate check runs outside a transaction, and a payment keeps only its last event id, which a reversal overwrites. So the status check under the row locks in `recordPayoutOutcome` and in `PayPalCheckoutService.settle`, not this check, is what makes a replay harmless. A `refused` signature usually means a stale `PAYPAL_WEBHOOK_ID`. Until it is fixed, reversals after payment are never credited back, because they arrive only by webhook, and a PayPal cash-in waits for its collector to come back before it is credited.

#### `apps/api/src/modules/pay/paypal-checkout.service.ts`

About 3 minutes. It builds on T8.6, T8.7, T15.2 and T15.3.

`PayPalCheckoutService` runs a cash-in by PayPal checkout, the Orders v2 API. The collector pays from a PayPal account or by debit or credit card on PayPal's own page, and the wallet is credited when PayPal confirms the capture, with nobody approving it. `paypalCheckoutOffered` is the switch `PAYPAL_CHECKOUT_ENABLED`, off by default. `paypalCheckoutAccepted` also lets the sandbox provider take a checkout with the switch off, because it moves no money and production refuses it, so the tests can run the whole flow. The switch does not loosen the production checks in `env.ts`, which still want PayPal and its three keys.

`start` checks the route, the switch and the cash-in limits. It claims the idempotency key by inserting a `pending` `external_payment` with the `provider_ref` `paypal_checkout:<route>:<userId>:<key>` through `onConflictDoNothing`, so two collectors never share a key. A second call with the key gets the same row, and another amount under it is `IDEMPOTENCY_KEY_REUSED`. Outside any transaction it calls `createCheckoutOrder` for the row's amount, with the row's id as `custom_id` and `cash-in-order:<id>` as PayPal-Request-Id, so a resend returns the same order. It saves the order id in `externalRef` with a conditional UPDATE that needs it still empty, and answers with PayPal's approval link. The adapter refuses a link that is not on PayPal's host for its environment. PayPal sends the collector back to `APP_BASE_URL` with `paypal=approved` or `paypal=cancelled` and the payment id.

`capture` finds the collector's own checkout row, or answers 404, and `captureRow` calls `captureCheckoutOrder` outside any transaction under the 20-second `CHECKOUT_PROVIDER_TIMEOUT_MS`, with `cash-in-capture:<id>` as PayPal-Request-Id. An order PayPal says it captured already is read back with `getCheckoutOrder`. `ORDER_NOT_APPROVED` is a 409 that keeps the row `pending`. Any other refusal means PayPal took nothing and is recorded as `failed`. No answer is a 502 that keeps the row `pending`, and a retry asks PayPal again under the same request id. `cancel` marks a `pending` row `cancelled` with a conditional UPDATE. `applyEvent` finds the row by order id, capture id or `custom_id` among this provider's checkouts, and refuses to choose when two rows match. `CHECKOUT.ORDER.APPROVED` runs `captureRow`, so a collector who never comes back is still credited.

`settle` records every answer, the capture's and the webhook's alike. It locks the payment row `FOR UPDATE`, then the wallet with `lockWallet`. A report whose order, capture or `custom_id` is not the row's changes nothing. A row already `succeeded`, `reversed` or `refused` changes nothing either, except that it keeps the first webhook event id it saw, so a redelivery is a `duplicate`. A pending capture stores its capture id and credits nothing. A failure marks a `pending` row `failed`. A completed capture of exactly the row's amount and currency writes one `credit_topup` for the full amount, stores the capture id and PayPal's fee, emits `topup_settled` and audits `payment.cash_in_settled`. It credits a row marked `failed` or `cancelled` too, because PayPal holds the money and the collector is owed it. Any other amount, or a capture taken back before it was credited, marks the row `refused`, credits nothing and is logged as an error for an admin to settle in PayPal. So the capture's answer and the webhook, in either order and any number of times, credit once, and `ledger_record_one_credit_per_payment` refuses a second credit if this logic were ever wrong.

A `PAYMENT.CAPTURE.REVERSED` or `REFUNDED` event for a `succeeded` row goes to `takenBackAfterCredit`, which logs and reports it and changes nothing. For a row an administrator has already marked `reversed` it answers `duplicate` and reports nothing, because the chargeback is recorded and following the old advice would only meet a 409. An admin records it with `POST /finance/chargebacks/:paymentId`, because `ChargebackService` already reverses a `succeeded` top-up once. Applying it from the event is not built yet, and this method is where it goes. PayPal's fee is Bault's cost. The collector is credited what they paid, and the fee is shown beside revenue in the monthly summary.

#### `apps/api/src/modules/pay/crypto-checkout.service.ts`, `packages/adapters/src/crypto.ts`

About 2 minutes. It builds on the PayPal checkout above.

`CryptoCheckoutService` runs a cash-in in crypto through Coinbase Commerce, which prices the charge in dollars and converts what the payer sends, so the wallet is credited exactly the dollars the collector chose, with nobody approving it. It is behind `CRYPTO_CHECKOUT_ENABLED`, off by default. With it off, `POST /finance/checkout/crypto`, `GET /finance/checkout/crypto/:paymentId` and `.../cancel` answer 404 and `routes` lists no crypto route, unlike PayPal checkout, which the sandbox takes with its switch off. `CRYPTO_PROVIDER` picks the processor, `sandbox` by default or `coinbase_commerce`, and `env.ts` wants `COINBASE_COMMERCE_API_KEY` and `COINBASE_COMMERCE_WEBHOOK_SECRET` with the second, and refuses the switch on in production with anything but Coinbase Commerce. `createCryptoProvider` never builds the sandbox in production, where a processor that refuses every call stands in until the account exists. `start` checks the limits, claims the key with a `pending` `external_payment` whose `provider_ref` is `crypto_checkout:<userId>:<key>` and whose `provider` is `coinbase_commerce` or `sandbox`, and outside any transaction asks for a `fixed_price` USD charge with the row's id in its metadata. The charge id goes into `externalRef` by a conditional UPDATE that needs it still empty, because the charges API has no idempotency key, so a replay reads the charge back with `describeCharge` instead of opening another. The answer carries the hosted page, which the adapter accepts only on https `commerce.coinbase.com`, and Coinbase sends the collector back to `#/wallet/cash-in` with `crypto=returned` or `crypto=cancelled`. `describe` reads a pending charge back and settles it when the processor already says confirmed or failed.

The webhook is `POST /webhooks/crypto`, `@Public` and exempt from the Origin check like the PayPal one, and `main.ts` keeps the raw bytes of that one path so the signature is checked against exactly what was sent. With the switch off it answers 404, unless the provider is `coinbase_commerce`, so a charge paid just before the switch went off is still credited. The adapter's `verifyWebhook` compares the `X-CC-Webhook-Signature` header with an HMAC SHA-256 of the raw body under the shared secret, in constant time, before it parses anything, and a mismatch is a 400 `webhook_unverified`. The sandbox signs with the published `SANDBOX_CRYPTO_WEBHOOK_SECRET`, which is why it may never run in production. An event id already on a payment is a `duplicate`. `settle` locks the row, refuses a report whose charge or `customId` is not the row's, and on `charge:confirmed` for exactly the row's amount in USD writes one `credit_topup` the way PayPal checkout does, emits `topup_settled` and audits `payment.cash_in_settled`, also for a row the collector had cancelled, because the money arrived. Another amount marks it `refused`. `charge:failed`, which Coinbase sends for an expired charge too, marks a `pending` row `failed`. `charge:pending` changes nothing, and `charge:delayed`, a payment after the charge expired, is logged and reported for an admin to resolve in Coinbase Commerce, after which its `charge:confirmed` credits it. The adapter never logs the key, which travels only in the `X-CC-Api-Key` header. `tests/integration/pay-cash-in-crypto.test.ts` runs the flow on a second API with the switch on, and `tests/contract/crypto-adapter.test.ts` holds the adapter to Coinbase's request and signature formats.

#### `apps/api/src/modules/pay/chargeback.service.ts`

About 1.5 minutes. It builds on T8.8, T6.7 and T14.3.

`ChargebackService` lets an admin record a chargeback, a settled cash-in that the payer or their bank took back. It is manual because the provider or the bank reports it outside the API. `record` handles a top-up. It locks the `external_payment` `FOR UPDATE`, and the payment must be a `succeeded` top-up. `recordCashInRecall` handles a cash-in that arrived as a reviewed wallet request, which has no `external_payment` row. It locks the `walletRequest` `FOR UPDATE`, and the request must be a `completed` cash-in. The credit it takes back is the ledger row `settledLedgerId` names, and a `chargeback` row with `reference_type = 'wallet_request'` on the same request means it was already taken back. Both then take the wallet lock and call `takeBack`, which checks no balance, so a chargeback may push the wallet negative. `takeBack` writes a `chargeback` debit for exactly the amount credited, referencing the payment or the request. Unless `chargeFee` is false, it also writes a `charge` under `chargeback_fee` with `chargebackFee: true` and a `fee` debit of `CHARGEBACK_FEE_MINOR`. It audits `payment.chargeback` and emits `payment_reversed`, with the payment or the request as the target. The payload's `kind` is `payment` for a top-up and the request's own `fundingSource` for a recalled cash-in, so the collector's notice names a bank transfer and the paying bank only when that is how the money came, and names PayPal for PayPal. `record` then marks the payment `reversed`. A second call on the same payment finds `reversed`, and a second call on the same request finds the earlier `chargeback` row, and either gets a 409, so the customer is debited once. `reversible` lists the 100 newest of the `succeeded` top-ups, PayPal checkout cash-ins among them, and the completed cash-in requests not yet taken back, each row carrying `kind` (`external_payment` or `wallet_request`).

#### `apps/api/src/modules/adm/accounting.service.ts`

About 3 minutes. It builds on T8.1 and T8.10.

`AccountingService` holds the accountant's reports, which are read-only and for admins. The ledger is single-entry, so a fee leaves a customer and reaches no Bault account, and this file computes revenue from the rows. `ledgerCsv` reads pages of 2,000 rows ordered by `occurred_at` and `id`, each starting after the last row of the one before, so no row repeats. The cursor stays Postgres text so microseconds survive. `csvField` puts an apostrophe before a text cell that starts like a formula, so a spreadsheet shows it as text. `decimalAmount` uses integer arithmetic, so no rounding error creeps in. `parseDayRange` includes both days, in UTC, up to `MAX_EXPORT_DAYS`, which is 366. `parseMonth` reads `YYYY-MM`, and `recordExport` writes the audit row `accounting.ledger_export`.

`summary` has four parts. `byType` counts and totals each type and direction. `revenue` nets the `fee`, `service_charge` and `interest` rows and splits them into `REVENUE_LINES` by snapshot key and reference. A `shipping_refund` or `service_refund` credit comes off the line its charge was counted on. A custom request's refund comes off `custom_request_fee`, and the rest come off `service_charge`. Their total is `refundsMinor`. Revenue also subtracts `cashOutFeesReturnedMinor` and shows the carrier cost beside the total. It shows `cashInProviderFeesMinor` there too, the fees PayPal kept on the PayPal cash-ins credited that month, which Bault pays and nothing takes off revenue. `customerMoney` gives top-ups in, withdrawals out net of `payoutsReturnedMinor`, and chargebacks. `balancesHeld` sums every wallet at month end, or now for the current month, with the platform account apart. `reconciliation` gathers top-ups, payouts, withdrawal debits and rows citing a missing payment, and passes them to `reconcile`. It counts `manualCashIns` apart, to be checked against the bank and PayPal statements, because no provider reports them.

A new refund type must go into both the revenue query and `refundsMinor`, or its money stays counted as revenue. The platform account is found by `PLATFORM_EMAIL`, which `HouseStoreService` and `ServiceRequestService` also hard-code, so change all three together, with a new migration for the row that `0038` writes. A fee that matches no snapshot key and no reference lands in `other_fee`.

#### `apps/api/src/modules/adm/reconciliation.ts`

About 2 minutes. It builds on T8.10.

This file holds the pure rules for whether external payments and ledger rows agree. `reconcile` returns `checked`, `matched`, `mismatches` newest first, and `pending`, the payments still waiting for an answer.

A top-up that is `succeeded` or `reversed` needs exactly one `credit_topup` for its amount. With no credit it is `succeeded_without_credit`, with two or more it is `duplicate_credit`, and with a wrong amount it is `credit_amount_mismatch`. A `reversed` one also needs `chargeback` debits that add up to its amount, or it is `reversed_without_chargeback` or `chargeback_amount_mismatch`. A top-up in any other status with a credit is `credit_without_settled_payment`. A chargeback on a top-up that is not `reversed` is `chargeback_without_reversal`. A `pending` top-up with no mismatch goes under `pending`. Any other row citing a top-up is `unexpected_ledger_row`, and a row citing a missing payment is `ledger_references_missing_payment`.

A payout needs a withdrawal debit of the same user with its reference, or it is `payout_without_withdrawal`. A `failed` payout with no withdrawal counts as matched, because no money moved. The payout must equal the debit less the fee, or it is `payout_amount_mismatch`. A `failed` or `reversed` payout must have its whole debit credited back, or it is `payout_failed_but_debited`. A `pending` payout with no mismatch goes under `pending`. A withdrawal debit that no payout vouches for is `withdrawal_without_payout`.

Matching uses the user and the `provider_ref`, which is the `payoutKey`, so one account's debit cannot vouch for another's payout. When a debit's request has no `payout_payment_id`, the query reads `payoutRef` and `feeMinor` from its `completed` event, and its withdrawal is the gross.
